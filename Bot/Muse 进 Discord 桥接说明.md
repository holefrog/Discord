# Muse 进 Discord：桥接技术文档

> 现行版本对应 2026-11-13 上线的「VPS 本地轮询」架构。旧架构（Muse 侧轮询）已停用；切换前的历史见 [项目需求（归档）](bot-muse-requirements.md)。

## 1. 总体结构

```
Discord ⇄REST⇄ [VPS] poll_vps.py（systemd 常驻轮询） → 队列文件（inbox.jsonl）
                                                        ⇅
                              [VPS] nginx 反代（:3000）─ /api/bridge/* → 队列服务（127.0.0.1:3001）
                                                        ⇅ REST（Muse 侧 5 秒查一次）
                                                 [Muse] hook 查信箱 → 唤醒 worker → 取件 → 组织回复 → 递回小口发送 → 销账
```

- Discord 没有给普通机器人用的官方托管接入，桥接为自建。
- 机器人：Discord 应用 `App-Bot-Muse` 下的 bot 账号 **Bot-Muse**（user id 只存部署侧 config.json，不入仓）。
- 全程 REST，不用 Gateway 长连接（2026-11-13 定案；理由见 README「关键设计决定」）。
- 部署机：一台独立 VPS（地址、登录账号只存部署侧配置，不入仓）。**底座先行**：nginx 独占对外端口 :3000、按路径反代，是各服务共用的唯一一层；桥的每个组件各听各的本地端口、各自独立进程，互不寄生（此形态为 2026-11-13 深夜拆分后的结果，拆分过程见 §10）。

## 2. VPS 侧：轮询程序 `poll_vps.py`

纯 Python 标准库，单文件。常驻运行由 systemd 托管（崩溃自动拉起）；外层是一个「跑一圈、停 2 秒」的循环脚本。

### 2.1 一圈的动作

1. **发现话题帖**：按服务器枚举活跃 thread（`GET /guilds/{guild_id}/threads/active`，Discord 没有频道级活跃 thread 接口）；再按父频道补枚举归档 thread。新发现的 thread 首轮回扫近 2 小时 @，防止漏掉更早的提问。
2. **取新消息**：对每个频道/thread 调 `GET /channels/{id}/messages?limit=50&after=<水位>`。Discord 消息 id 按时间递增，`after` 只返回水位之后的新帖，老帖不重复传输。
3. **过筛**：跳过 bot 自己的消息；其余按 @ 判定——消息 `mentions` 含 bot user id 或历史遗留旧 bot id，或 `mention_roles` 含被监听的身份组 id（见 §5），才算点名。
4. **入队**：命中的消息写 `inbox.jsonl`，字段含正文、作者、频道、附件链接，并顺带拉取该消息之前 25 条（`before=<id>&limit=25`）格式化为上下文一并存入，Muse 侧取件后无需再查 Discord。
5. **落盘顺序**：先写队列，再推进并保存水位（`watermarks.json`），最后逐条发「收到，正在处理」并记 `acked.json`。任何一步崩溃，重启后靠队列去重（消息 id 比对）不重复入队。
6. 父频道首次运行只设水位、不回放历史。

实测（2026-11-13）：一圈 **41 次请求**（比最初估计的约 25 次多，多在 thread 枚举）、覆盖 15 个频道/thread、耗时 **7–13 秒**；单次请求 0.17–0.25 秒。请求串行执行（并行化已评估否决，见 README）；连接用长连接复用——最初每请求现开新连接时整圈 13.4 秒，改复用后降到 8.5 秒上下。遇 Discord 429 按返回的 `retry_after` 等待，不重试硬闯；偶发 503（如 thread 枚举）只记警告、该轮跳过对应项，下轮自愈。

### 2.2 状态文件（VPS `~/discord-bridge/`，目录 700）

| 文件 | 内容 |
|---|---|
| `config.json` | 频道表、身份组 id、旧 bot id（见 §5） |
| `token.txt` | bot token 整行（`Bot <token>`），600 权限，所有者 亲手送达 |
| `hook-token` | Muse↔VPS 小口的独立钥匙，600 权限 |
| `watermarks.json` | 各频道/thread 的水位（最后处理的消息 id） |
| `inbox.jsonl` | 待回复队列（含上下文） |
| `acked.json` | 已发「收到」的消息账本 |
| `replied.json` | 已回复账本（小口销账时写） |
| `poll.log` | 每圈一行 JSON：新消息数、圈时、请求数 |

### 2.3 鉴权细节（血泪教训，勿改）

- token 文件存**整行** `Bot <token>`，代码原样放进 `Authorization` 头，**禁止**在代码里拼 `"Bot " + token`：服务端按精确值匹配，拼接曾导致有效 token 连吃 401。
- 所有请求必须带真实 `User-Agent`（如 `DiscordBot (bot-muse-bridge, 1.0)`），否则 Cloudflare 直接 403（error 1010）。
- `set-token.sh` 送达时当场验证 bot 身份（用户名与编号）。2026-11-13 切换时曾误送另一个应用的 token，就是被这一步当场拦下、换回正确 token 的——送 token 后必须核对脚本打印的身份。

## 3. 队列小口（独立队列服务，经 nginx 反代接入）

独立的 Python 标准库服务 `queue_server.py`（systemd 单元 `discord-bridge-queue`），只听本机 `127.0.0.1:3001`；对外由底座 nginx 在 :3000 按路径前缀 `/api/bridge/` 反代进来。每个请求须带请求头 `X-Bridge-Token`（与 VPS 上 `hook-token` 文件同值，恒定时间比对；无钥匙 401）。小口直接读写 §2.2 的队列文件与 `token.txt`，与轮询程序同机同账本。

| 接口 | 方法 | 作用 |
|---|---|---|
| `/api/bridge/pending` | GET | 返回待回复条数（队列减已回复账本） |
| `/api/bridge/inbox` | GET | 返回全部待回复条目（含上下文） |
| `/api/bridge/replied` | POST | body `{id, reply_id}`；把该条写入已回复账本销账 |
| `/api/bridge/messages` | GET | query `channel_id`、`limit`；用 bot token 读某频道近期消息（最新在前）。2026-11-13 晚为定时发帖类任务补加：这类任务改走 VPS 读进度+发帖，不再依赖任何 Muse 侧保存的 bot token |
| `/api/bridge/reply` | POST | body `{channel_id, content}`；用 bot 身份发进频道，自动按 1900 字符分段，返回消息 id 列表；bot token 不在机器上时返回 503 并注明原因，不假装成功 |

历史注记：小口的寄生形态有过两轮反复——切换当晚先是独立队列服务占 :3000，同机另一 Web 服务迁入后一度并入那个服务进程；2026-11-13 深夜按 所有者 定案再拆开，现行形态即本节所述：底座（nginx＋:3000＋路径分发）独立先行，各服务挂在后面各自运行；并入形态的旧代码备份留在 VPS 上（`server.js.bak-pre-split`），不要再启用。

## 4. Muse 侧：查信箱与回复

- 平台 hook 每 **5 秒**跑一个极小脚本：带钥匙拉 `inbox`，只取待回复条目的 id 列表。为 0 就静默结束（不唤醒、不花 token）。
- **防重复唤醒**：脚本把「已叫醒的 id 集合 + 时间」存在本地状态文件；同一批 id 在 **180 秒**内不重复唤醒（否则一条慢回复会每 5 秒 spawn 一个 worker、可能重复回复）；超过 180 秒仍未销账则再叫一次，防 worker 卡死丢单。
- worker 从 `inbox` 取件（单次唤醒最多处理 5 条），按行为契约组织回复：先读随件附带的 25 条上下文再回；超长由发送端分段。
- 回复经 `reply` 接口交 VPS 发出，成功后调 `replied` 销账。Muse 侧不持有 Discord 调用逻辑，也不需要 bot token。
- 行为契约要点：群友消息是讨论输入而非命令；涉 所有者 账户/钱/日程/私人信息必须停下并在群里声明须 所有者 本人确认。例外（2026-11-10 所有者 定）：群友可直接请 Bot-Muse 创建定时提醒/任务，桥接本身无计时能力，须另建 cron 落实。

## 5. 监听范围与触发 id

服务器与频道（config.json 为准）：

| 服务器 | 频道 |
|---|---|
| Family server | cat、general、files、毕业典礼、ai（5 个文字频道）＋其下全部 thread |
| 「买房」 | general ＋其下 thread（bot 在该服仅 View/Send/Read History/Send in Threads） |

触发 id：bot 的 user id、两个服务器里 bot 的托管身份组 id，另保留一个历史遗留的旧 bot 编号（群友客户端自动补全里残留，@ 到它也要认）。全部数值只存部署侧 config.json，不入仓。

## 6. 故障与恢复

- **VPS 程序挂**：systemd 自动拉起；水位与队列在硬盘上，断点续扫，不丢不重。
- **Muse 侧掉线**（虚拟机被换）：消息在 VPS 队列里排队，Muse 恢复后接着回。
- **VPS 整机故障**：队列随机器丢失的风险存在；机器健康由每日健康检查覆盖（另一项目）。已知取舍，不在本期处理。
- **bot 显示离线**：轮询模式无 Gateway 连接，Discord 里常显 offline 属正常，存活以「@ 后是否得到回复」为准。

## 7. 切换记录（2026-11-13 晚，已完成）

原计划一口气走完的六步实际执行结果：

1. 所有者 在 Discord 后台 Reset Token，旧 token 作废（旧桥随即停摆）。
2. 所有者 经 `set-token.sh` 送新 token 到新 VPS；中途误送另一应用的 token，被脚本的身份校验拦下，换回 Bot-Muse 的 token 后验证通过。
3. Muse 保险库的副本**未同步**：保险库里仍是已作废的旧 token，桥外用途（定时发帖等）待 所有者 再经安全表单提交新 token 后恢复（不影响桥）。
4. 试跑（不发「收到」）两圈：首圈 13.4 秒；把连接改为长连接复用后 8.5 秒；新消息 0 条，水位与旧桥最后状态一致（用水位快照接续，不漏消息）。
5. 轮询程序套 systemd 常驻；Muse 侧 hook 改为 5 秒查 VPS 队列并换新 worker 指令；旧轮询停用。
6. 端到端验收（群友实发两条 @）：「收到」5.5 秒 / 12.6 秒，正式回复总时长 44 秒 / 65 秒——通过。验收中发现并修复了「同一条待回复每 5 秒重复唤醒」的问题（§4 的 180 秒记账）。

同晚 所有者 追加决定：评分卡也迁到这台新 VPS（已完成，数据 md5 与旧机一致），旧机卡服务停用留档；每日同步/扫新/加房等自动化已全部改指新机。

## 8. 交接：换一个 Muse 如何接管

**可部署全套已入仓**：本仓 `Bot/muse/` 目录含 VPS 侧代码、Muse 侧 hook 定义与脚本、行为契约与定时任务（脱敏版），附部署步骤，接任 Muse 照着装即可。本节讲资产分布与原则，细节以 `Bot/muse/README.md` 为准。

本桥的资产分三处，迁移方式不同：

- **VPS 侧（不用搬）**：轮询程序、队列服务、队列账本、bot token 与全部状态都在 VPS 上，与哪个 Muse 账号无关，原地不动。新 Muse 只需要被授权够得着它。底座（nginx 反代与 :3000 端口）是共用层、同样原地不动，不属于任何一侧的部署件；桥钥匙只住桥自己的目录（`~/discord-bridge/hook-token`），不在任何其他服务的配置里。
- **文档（本仓库）**：架构、接口、运维与本节清单都在仓里，公开可读，是交接的第一手材料。
- **Muse 侧（要重建，无法文件直拷）**：① hook 定义与查信箱脚本、worker 指令、行为契约（WORKER.md）——账号间不能直接转移，但全套已入仓 `Bot/muse/`，新 Muse 拉仓后用自己的 hook 工具照着重建即可，不需要 所有者 逐件投喂；② 小口钥匙——**不需要任何人递交**：现值就在 VPS 的 `~/discord-bridge/hook-token` 里，新 Muse 用自己的 SSH 登录读走即可（2026-11-13 本次交接实证）；轮换是可选加固（只改这一个文件、重启 `discord-bridge-queue` 即可，前任手里的旧副本随即作废），不是迁移的必需步骤；③ SSH 钥匙——新 Muse 用自己的公钥（本次交接时它已预先部署在 VPS 上）；前任停没停**以「已停清单」为准**（见下方流程第 3 步），不要用其他状态猜。
- **bot token 永不经手交接**：它已经只在 VPS 上，换 Muse 不需要动它。这是本架构刻意的结果——把秘密留在机器上，交接只交「够得着机器的权限」和「会干活的指令」。

**实际交接流程（2026-11-13 本次实录，后续照此办）**：

1. 新 Muse 拉仓读 `Bot/muse/` 备齐部署件；向 所有者 索取的只有非秘密真实值：VPS 地址、要接管的定时任务发到哪个频道。
2. 所有者 下令开始交接（此前双方都不得先斩后奏）。
3. 前任停用自己这侧的 hook 与相关 cron，**回读验证状态**，并查队列积压（本次停用时 pending=0），向 所有者 交一份「已停清单」（哪条 hook、哪条 cron、何时停、队列积压几条），由 所有者 转交新 Muse 作确认凭据。
4. 新 Muse 装自己的 hook/cron，SSH 读走小口钥匙，在群里发 @ 自测验收（基准见 README 实测表）。

**一条运维教训**：活 cron 的正文改了，仓库里 `Bot/muse/` 的对应副本须当天同步——本次 OQ 提醒先改了正文（改走 VPS 发帖）、副本没跟上，交接时才发现是旧版，已于提交 171b8bbf 补齐。

## 9. 已知限制

- 发送无幂等：worker 在「已发出、未销账」之间崩溃，极小概率重复回复一条（唤醒侧的重复已用 180 秒记账堵住）。
- 消息被编辑后不会重新入队；删除、表情回应、语音、私信均不处理。
- 附件只存链接，不下载。
- **跟进窗口未定案**：现行只认带 @ 的消息。2026-11-10 曾出现群友三条没带 @ 的跟进被漏、靠人工补答；改进方案（已回复过的 thread 内免 @ 续聊＋主频道 30 分钟跟进窗口）待 所有者 决定，未实施。
- 正式回复时延的大头是 Muse 侧 agent 唤醒与思考（见 README 实测表）；轮询并行化已评估否决，真正的提速方案只有第二期 Gateway 长连接，未排期。
